# Japan snowfall（日本の降雪量）

[English](README.md) · 日本語 · [繁體中文](README.zh-Hant.md)

日本のスキー場の過去の降雪量を、リゾートの宣伝数値ではなく気象庁の観測所の記録から集計したサイトです。静的サイトで、ビルドツールも依存ライブラリもなく、標準ライブラリだけで動きます。

## 公開場所

<https://japan-snowfall.bill-chung.com/> — <https://billcchung.github.io/japan-snowfall/> からも見られます。

GitHub Pages が `main` のリポジトリ直下から配信しています。`main` に push すると再デプロイされ、ビルド手順はありません。独自ドメインは `CNAME` で設定されており、リポジトリ設定でドメインを消すと Pages がブランチからこのファイルを削除します。ドメインを変更するとき以外は触らないでください。

## 対象範囲

40のリゾートすべてにシーズン記録があります（北海道21、本州19）。旅行プランナーと推移ページには、観測所ごとに `daily` で埋める日別キャッシュも必要です。週次ワークフローが両方を最新に保ちます。

ワークフローが push できない場合は、**Settings → Actions → General → Workflow permissions** が *Read and write* になっているか確認してください。

ローカルで実行する場合:

```bash
python3 jma_snowfall.py discover
python3 jma_snowfall.py fetch
python3 jma_snowfall.py verify
python3 jma_snowfall.py daily
python3 jma_snowfall.py survey
python3 site.py build
```

標準ライブラリのみを使い、気象庁がサイトへの過度なアクセスを控えるよう求めているため、全体にレート制限をかけています。`discover` は都道府県ごとに1リクエストで約50件です。`fetch` は地上観測所ごとに1件、AMeDAS 観測所は記録のある年ごとに1件で、合計約1,400件です。`daily` は観測所×月ごとに1件で、初回は約14,000件、キャッシュ済みの月を飛ばす週次実行では約300件です。`survey` は降雪を記録している観測所ごとに1件で約350件、リゾート一覧とは独立しており、気象庁の寒候年の表を使うため、1観測所の全期間が1リクエストで取れます。`fetch` と `daily` にリゾート名を渡すと一部だけを実行でき、別のデータ元に属するリゾートは無視されます。

## 言語

サイトは英語、日本語、繁体字中国語で表示できます。言語は `?lang=ja` / `?lang=zh-Hant` / `?lang=en` があればそれを使い、なければ訪問者が最後に選んだ言語（ブラウザに保存）、それもなければブラウザの言語設定から決めます。中国語の設定はすべて繁体字になります。ページナビゲーション右端の切り替えボタンで、選択内容を保ったまま、その場で言語を変えられます。ページ間のリンクも選択を引き継ぎます。

文言はすべて `locales/*.js` にあり、それぞれ `I18N.add("<code>", {...})` の中に置いた厳密な JSON のテーブルです。テンプレートの固定テキストには `data-i18n="key"`（属性は `data-i18n-attrs="attr:key"`）を付け、マークアップには英語を残してあるので、スクリプトを無効にしても読めます。スクリプトで組み立てる文は `T("key", {vars})` を通します。`{name}` はプレースホルダーです。`.one` と `.other` の形を持つキーは複数形で、`{n}` から `Intl.PluralRules` が選びます。日本語と中国語は `.other` だけで足ります。選んだ言語にないキーは英語にフォールバックします。

文言を触ったら `python3 i18n_check.py` を実行してください。ある言語にないキー、食い違うプレースホルダー、コードが要求しているのに存在しないキー、テンプレートのマークアップ内の英語が `locales/en.js` と合わなくなった場合に失敗します。

リゾート名とスキー場エリアの説明は UI ではなくデータです。`resorts.json` の `names` と `reference.json` の `areas_i18n` に、それぞれ `ja` と `zh-Hant` をキーとして置きます。未設定なら英語で表示します。観測所名、都道府県、読み仮名は気象庁の日本語がそのまま全言語で表示され、各ページ見出しの下の `降雪の深さ…` も同じです。地域見出し（`Hokkaido`、`Tohoku` など）はロケールファイルの `area.<名前>` にあります。

言語を追加するには、`locales/en.js` を `locales/<code>.js` にコピーして翻訳し、各テンプレートに `<script src="locales/<code>.js">` を足し、`i18n.js` の `LANGS` と `normalise()` にコードを加え、`names` と `areas_i18n` を用意します。既定のフォントにその文字体系がなければ `site.css` にフォントの指定も加えてください。

## 国を追加する

`site.py` は特定のデータ元の索引やコード表を開かないので、2つ目の国には、取得スクリプトと台帳エントリが必要で、ここの変更は不要です。

1. `resorts.json` に、独自の `source` と、そのサービスが必要とする `station` オブジェクトを持つエントリを追加します。
2. リゾートごとに `data/<resort>.csv` を出力する取得スクリプトを書きます。列は `resort, source, station, station_id, station_m, region, season, oct, nov, dec, jan, feb, mar, apr, may, season_total_cm, incomplete, note` です。`station_m` は空でも構いません。`season` は `YYYY/YY` の形式です。
3. 必要なら `data/daily/<source>-<station_id>.json` も書きます。キーは `"YYYY-MM"` で、各値は1日1つの値を持つ `snow` と `depth` の配列です。これがないリゾートは記録ページには出ますが、プランナーと推移には出ません。
4. `python3 site.py build` を実行します。

`station_id` はデータ元の中で一意であれば足ります。日別ファイル名にデータ元の名前が付くので、2つのサービスが観測所に同じ番号を振っても衝突しません。

北半球専用の部分が2つ残っています。シーズンは10月1日〜5月31日で、1か所（`site.py` の `SEASON_MONTHS`）で定義して各ページに出力しますが、シーズンの年を決める規則は冬が年をまたぐことを前提にしているため、南半球のリゾートには一般化が必要です。また `verify` は日本しか確認しないので、2つ目のデータ元には独自の基準値が必要です。

## 数値の読み方

要素は降雪の深さ月合計で、日ごとの新雪の深さを月で合計したものです。積雪の深さ（最深積雪）でも、リゾートが宣伝する累積値でもありません。

気象庁は雪を寒候年（8月1日〜翌年7月31日）で整理しているため、スキーシーズンは元の表の2行にまたがります。10月〜12月は一方の暦年から、1月〜5月は次の暦年から取ります。そのまま読むとシーズン合計がすべて誤りになります。スクリプトがこれを処理しています。

シーズンは10月1日〜5月31日で、日本に必要な範囲より広く取っています。アルプスやロッキーを載せるときに、保存済みのファイルをすべて移行しなくて済むようにするためです。ほとんどの日本の観測所では、10月と5月はほぼゼロです。

観測所があるのは山ではなく谷あいの町です。倶知安の観測所はニセコの山頂より約1km下、白馬は八方の麓付近、蔵王は山形市内にあります。リゾートは、まず自身の過去と比べれば確かですが、他のリゾートとの比較は目安にとどめてください。サイトは観測所とのあいだの標高差を表示するので、自分で判断できます。

ニセコの系列は Ski Asia の公表値と照合済みです。2025/26は751cm、2019/20は685cm、1969/70は2,019cm、直近10年平均は849cmで、すべて一致しています。`verify` は実行のたびに73シーズンすべてを手書きの書き起こしと突き合わせます。

それらの公表値は11月〜4月の値なので、サイトでは Nov–Apr 列の合計がそれにあたり、シーズン合計とは違います。シーズンを10月〜5月に広げたため、10月や5月に雪が降った年は両者が異なります。2025/26は11〜4月が751cm、全期間では752cmです。日本のすべてのリゾートを通すと、10月は全降雪量の0.21%、5月は0.16%にすぎません。この2列はアルプスやロッキーのためのものです。

## 既知の弱点

**志賀高原**は野沢温泉の観測所を借りていますが、そこは標高が750m低く、尾根の反対側です。高原上に観測所はありません。仮の値として扱うか、`resorts.json` から外してください。

**観測所の種類によってエンドポイントが違います。** 地上観測所は `monthly_s3.php?view=p6` で全期間が1つの表にまとまります。AMeDAS 観測所にはそれに相当するものがなく、観測所の索引に `annually_a.php` と `nml_amd_*` の平年値しかないため、`monthly_a1.php?year=YYYY` を暦年ごとに1リクエストで取ります。風・気温・日照を省く観測所は列が少なくなるので、列の位置は行末から数えます。雪の3列は常に最後です。

**日別の表も同じように分かれますが、こちらは扱いやすいです。** 地上観測所は `daily_s1.php?year=&month=`、AMeDAS は `daily_a1.php` を使います。月別の表と違い、種類ごとに列数が固定で、21列と18列です。観測していない要素は列が落ちるのではなく `///` で返ってきます。雪は末尾から数えます。地上観測所の行は末尾に天気概況の2セルがあるので、新雪は `-4`、積雪深は `-3`、AMeDAS は `-2` と `-1` です。日別の合計は月別の合計と完全に一致するので、正しい列を読んでいるかを確かめる最も手軽な方法です。

**気象庁は地上観測所の月別表で、年のセルの閉じ `</td>` を省略します。** そのため単純に `<td>…</td>` で切ると、年と1月の値がくっついて、すべての行で列数が合わなくなります。`cells()` が開始タグで分割しているのはそのためです。表が0行にパースされたら、まずそこを疑ってください。

**降雪観測所の4分の1は過去のものです。** 地図にある336観測所のうち26は2020年より前に報告をやめ、そのうち4つは1997年で、元データのどこにも閉鎖とは記されていません。したがって「直近N年の記録」で計算する数値は、稼働中の観測所と閉鎖済みの観測所を比べてしまいます。`survey` が全期間を保存し、地図があなたが選んだシーズンの範囲で平均し、その範囲に5シーズン未満しかない観測所を外すのはそのためです。

**観測所の探索**は、気象庁の地域地図にある `viewPoint(...)` の呼び出しを解析します。その記述が変わっても、番号だけを拾うフォールバックはありますが、観測所名が失われるため、`fetch` は観測所が見つからないと報告します。

## 日本のリゾートを追加する

`resorts.json` に、観測所の正確な日本語名と地域コードを持つエントリを1つ追加し、日本語と繁体字中国語の名前を入れた `names` も加えます（[言語](#言語)を参照。省くと英語で表示されます）。`discover` のあとで `station_index.json` を grep して観測所を探し、その観測所の `"snow"` フラグが `true` であることを確認してください。AMeDAS 観測所の多くは風と気温を観測しても雪は観測せず、その場合 `fetch` は空の系列を書かずに拒否します。台帳の順序が表示順です。

データの帰属は [ATTRIBUTION.md](ATTRIBUTION.md) にあります。
